Second action of site-gate, and the actual "zero defects" enforcement.

Why: the site is already non-compliant — docs/findings.md §4 lists D1-D4, which a checker finds in seconds on every post. An absolute-zero gate would block all work behind a remediation pass, so the gate is a ratchet: fail on NEW violations, allow known ones.

Shape (confirmed): gate set = home, /blog, one post, one service page, /contact; 3 widths 390 / 768 / 1440. Violations recorded in a committed baseline file; the gate compares against it.

Hard rule: updating the baseline is an ask-gate. The harness may never edit the baseline to make itself green; a baseline change is a human-reviewed commit that says which violation was fixed or accepted. This is the equivalent of mastra-factory's "never weaken an ask-gate".

Open (does not block starting): which checks join the gate — proposed in docs/findings.md §6:
- build exits 0 AND the rendered HTML parses (catches the <p><div> in _layouts/post.html)
- internal links resolve (130 posts make renames expensive)
- diff scope: `git diff --name-only` stays inside the files the tweak names
- before/after screenshots at the three widths in runs/<id>/ — evidence for the human, not a gate condition
Tool choice also open: pa11y-ci vs axe-core driven by playwright. Node is available; chromium resolution matters (wereview-deps learned to take the playwright-bundle browser, never a snap fallback).

Depends on gate-ghpages-232: the gate must serve the same build that ships, so this lands after the container build exists.
